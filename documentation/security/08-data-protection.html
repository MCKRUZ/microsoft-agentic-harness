Chapter 08 · Data & Privacy

Data Protection & Privacy

The last of the seven defensive layers — layer 7: what the agent may see, what it may keep, and what it can be made to forget. The earlier layers stop an attacker from acting; this one governs the agent's relationship to data over time — per-tenant and per-user isolation, provenance, retention, and right-to-erasure. It is the difference between a system that can answer and a system you can put a customer's private knowledge into.

The two privacy boundaries

Memory makes an agent useful and dangerous in the same breath. The moment it remembers across sessions, two questions become security-critical: can one customer's knowledge leak into another's, and can one user read another user's private memory? The harness answers both with a single mechanism, but it is worth seeing them as two distinct lines.

Tenant ↔ tenant
The hard outer wall. One customer organisation's knowledge graph must never be visible to another's — not in retrieval, not in memory, not by accident. This is the boundary a multi-tenant SaaS lives or dies on.
User ↔ shared corpus
The softer inner wall, inside a single tenant. A user can see their tenant's shared corpus (documents and facts everyone in the tenant may use) plus their own private memory — but not another user's private memory. Net visibility: shared-in-tenant + mine, nothing else.

Both walls are enforced in the same place and by the same rule: a per-record check on every read and every write to the knowledge graph.

Per-record isolation: the visibility rule

The enforcement point is a decorator that wraps the knowledge-graph store (IKnowledgeGraphStore): src/Content/Infrastructure/Infrastructure.AI.KnowledgeGraph/Scoping/TenantIsolatedGraphStore.cs. It sits between callers and the real backend, and on every operation it asks two questions about each record before letting the caller see it or touch it. The questions run through IKnowledgeScopeValidator (src/Content/Infrastructure/Infrastructure.AI.KnowledgeGraph/Scoping/KnowledgeScopeValidator.cs), which checks tenant match plus dataset ownership.

The rule, stated plainly:

  • A node is visible only if its TenantId is null (a global record) or equals the caller's tenant; and
  • its OwnerId is null (the shared corpus) or the caller owns it.

Written as a truth table — both columns must land on a green cell for the record to be visible:

Record's TenantId Tenant check Record's OwnerId Owner check Visible to caller?
null (global) passes null (shared corpus) passes Yes
= caller's tenant passes null (shared corpus) passes Yes — tenant shared corpus
= caller's tenant passes = caller passes Yes — caller's own memory
= caller's tenant passes = another user fails No — another user's private memory
= another tenant fails (any) — No — cross-tenant, blocked outright

The net effect: a user sees their tenant's shared corpus plus their own memory — and nothing from other tenants or other users. The same check runs on writes, so a record can only be written into a scope the caller actually occupies.

!
The single-tenant switch is deliberate

When the MultiTenantIsolation config is disabled, all access passes — the decorator becomes a pass-through and the store behaves as a single shared graph. This is an intentional mode for single-tenant deployments, not a bug. If you run more than one customer on one harness, this switch must be on; treat it as a load-bearing setting and verify it in every environment.

Ambient identity propagation

The visibility rule is only as good as the identity it checks against. The hard part is making the caller's identity available everywhere it's needed — including in background work that runs after the HTTP response has already been sent — without manually passing a user/tenant parameter through every method in the call chain. The harness solves this with an ambient mechanism.

¶
AsyncLocal

A .NET mechanism that carries a value along an asynchronous call chain — including into background continuations spawned from it — without threading it through every method signature. Set it once at the top of a request and any code that runs as part of that request, however deep or however much later, can read it back. It is the right tool for "the current user" precisely because identity needs to follow the work, not the stack frame.

The accessor (src/Content/Infrastructure/Infrastructure.AI.KnowledgeGraph/Scoping/KnowledgeScopeAccessor.cs) stores the user/tenant/dataset identity in a static AsyncLocal, set once at request entry. From there it flows automatically into child dependency-injection scopes and into post-turn background writes — so a memory written after the response still lands in the right tenant and owner, with no extra plumbing.

Identity is captured at the entry point, after authentication, by one thin adapter per transport — mounted on every HTTP host, not just the agent hub. A host that forgets to mount it does not fall back to something safe: unscoped records are stored as global, so every caller can read them.

Transport Capture point What it does
HTTP (Agent Hub) src/Content/Presentation/Presentation.Common/Scoping/KnowledgeScopeMiddleware.cs Runs immediately after authentication and before authorization; calls KnowledgeScopeInitializer to pull userId/tenantId from the authenticated ClaimsPrincipal and seed the accessor. An authenticated caller whose identity cannot be resolved is rejected with 401 rather than allowed to proceed unscoped.
HTTP (Bundle API) The same class, mounted in src/Content/Presentation/Presentation.ExecutionApi/Program.cs Identical behaviour and identical position in the pipeline, so plans and records created by an externally-triggered bundle run are scoped exactly as agent-hub turns are. This host previously mounted no scope adapter at all, which meant bundle-created records were written unscoped — that is, global.
SignalR src/Content/Presentation/Presentation.AgentHub/Hubs/KnowledgeScopeHubFilter.cs The hub-filter equivalent for real-time connections; same KnowledgeScopeInitializer, same claims source, so streaming turns are scoped identically to HTTP turns.
i
Identity comes from claims, never from the request body

Both adapters read the user and tenant from the authenticated ClaimsPrincipal — the identity the platform proved during login — not from anything the caller can set in the payload. A request cannot ask to be treated as a different tenant; it is whatever its token says it is.

Memory namespacing

Isolation by filtering is the primary control. Namespacing is the belt-and-braces backup: identity is baked into the memory node's id itself. Memory node ids follow the pattern: 

memory:{tenant}:{user}:{key}

Because the tenant and user are part of the key, one user's memory key cannot collide with or address another's — even if the per-record isolation filter were somehow bypassed, there is no id a user could construct that names another user's memory without already knowing (and being) that user's scope. The id space itself is partitioned.

Enforced in all three local backends

Isolation that only holds for the in-memory development store would be a trap: it would pass every local test and then leak in production. The harness persists and filters OwnerId/TenantId in every local backend, so the same record-level boundary holds whichever store you deploy — this guarantee is local-storage-only; see the callout below for the remote-memory exception.

Backend File How isolation is persisted
In-memory (dev) src/Content/Infrastructure/Infrastructure.AI.KnowledgeGraph/InMemory/InMemoryGraphStore.cs Preserves OwnerId/TenantId on merge.
Neo4j src/Content/Infrastructure/Infrastructure.AI.KnowledgeGraph/Neo4j/Neo4jGraphStore.cs Persists owner_id/tenant_id; the Cypher uses coalesce so a write never null-clobbers an existing tenant.
PostgreSQL src/Content/Infrastructure/Infrastructure.AI.KnowledgeGraph/PostgreSql/PostgreSqlGraphStore.cs owner_id/tenant_id columns on kg_nodes and kg_edges, with indexes; self-initializes its schema.
!
Remote memory hosting is not yet covered by this guarantee

When AppConfig:AI:RemoteMemory:Enabled is true, recall is answered by an external avatar-hosting service whose contract does not currently filter by caller identity — two users of the same harness deployment can see each other's remote-stored facts via content search. This harness's own write-gate still scans everything it writes before it leaves this process, but it cannot verify content already sitting in the remote store from some other source. Until the remote contract enforces per-caller filtering and echoes a trust signal on recall, treat one AvatarId as a single shared trust boundary and provision a separate deployment per isolation boundary you need — enforced at startup via RemoteMemoryConfig.AcknowledgeSharedRecallBoundary.

Provenance: making every fact attributable

Isolation answers "who may see this." Provenance answers "where did this come from, and can I trust it." Every node and edge written to the graph is stamped — when GraphRagConfig.ProvenanceEnabled — by src/Content/Infrastructure/Infrastructure.AI.KnowledgeGraph/Provenance/DefaultProvenanceStamper.cs, which produces an immutable src/Content/Domain/Domain.AI/KnowledgeGraph/Models/ProvenanceStamp.cs record carrying:

Field Meaning
SourcePipeline Which ingestion/processing pipeline created the record.
SourceTask The specific task within that pipeline.
Timestamp When it was written (UTC).
SourceDocumentId The originating document — or null if the fact was synthesized.
ExtractionConfidence How sure the extractor was (0–1) — or null.
LastModifiedBy The actor responsible for the most recent change.
¶
Memory poisoning

An attack where a hostile party plants a false "fact" into the agent's memory during one session so that a later session retrieves it and is misled — the slow-burn cousin of prompt injection. Because the agent treats its own memory as trusted, a single poisoned record can quietly steer future answers. This is OWASP Agentic threat ASI06.

Provenance is the structural defence against it: every fact is attributable, so a downstream filter can act on memory whose SourcePipeline or SourceDocumentId is untrusted instead of blindly trusting whatever is in the graph. You cannot decide whether to trust a fact you cannot trace; the stamp is what makes the decision possible.

Trust-aware memory: the write-gate

The quarantine is not hypothetical — it is enforced on every write. KnowledgeMemoryService.RememberAsync runs an IMemoryWriteGate before anything is persisted. Content the gate judges untrusted is stored as MemoryTrust.Untrusted — quarantined rather than written as recallable — and the IsRecallable check is re-evaluated at read time, so a quarantined record never re-enters a prompt even if it slipped through. This directly closes the memory-poisoning (ASI06) path: a hostile fact planted in one session cannot silently steer a later one.

Compliance & retention

Knowing where data came from is half of governance; the other half is not keeping it longer than you're allowed to, and being able to prove what happened to it. A second decorator — src/Content/Infrastructure/Infrastructure.AI.KnowledgeGraph/Compliance/ComplianceAwareGraphStore.cs — handles the temporal and audit side:

  • On writes it stamps temporal metadata — creation time via TimeProvider.GetUtcNow() — and tenant metadata.
  • On reads it filters out expired nodes, so stale data simply isn't returned.
  • It emits a MemoryAuditEvent (Remember / Recall / Forget / Erasure, with ActorId, Timestamp and ScopeId) to IMemoryAuditSink. The default sink writes it to the structured log (AppConfig:AI:Rag:GraphRag:AuditSinkProvider, default structured_logging); it is not one of the hash-chained JSONL governance trails. Deletions record how many nodes and edges were removed, never their ids: memory node ids embed the owner and the memory key, so a deletion record that listed them would keep what was deleted.

Retention rules are not hardcoded: they come from IRetentionPolicyProvider, resolved per tenant and per dataset, so different customers and datasets can carry different lifetimes.

Retention periods outside the graph (#901)

GDPR's storage-limitation principle (Article 5(1)(e)) does not allow personal data to be kept with no end. Every store in the personal-data inventory declares how long it keeps what it holds, and a guard (EveryPersonalDataStoreIsDeclaredTests) fails the build if a store declares RetentionBasis.Unbounded without being on a list of known gaps that only shrinks (KeptForeverGaps). The stores with a period so far:

  • Conversations. A conversation with no new message for AppConfig:AI:Conversations:Retention:IdlePeriod (default 365 days) is deleted with everything found through it: its messages, observability sessions, spilled tool results, prompt-usage rows, token budget and call-once ledger rows. Reading a conversation does not reset the clock; writing to it does. ConversationExpiry deletes in the same stage order as erasure, under the conversation's turn lease, so a conversation with a turn running is never touched, and it asks only stores whose ErasureReach is NamedConversations, so the person's documents, plans, schedules and memories stay. Deleted bytes are cleared from the database files afterwards. A period under a day is refused at startup and by the sweep itself.
  • Prompt-usage records (when persisted) are deleted after AppConfig:AI:PromptUsage:Retention:RetainFor (default 90 days).
  • Plans. A plan nothing has happened to for AppConfig:AI:Planner:Retention:RetainFor (default 90 days) is deleted with its steps, outputs and execution log, whatever its state: finished, never run, or stopped waiting on an approval. Saving it, a step starting or finishing, and a log entry all count as activity. A plan a schedule runs, or a run is queued or parked on, is kept however long it waits: a quarterly schedule's gap is longer than the period. A plan deleted between being loaded and started is not run.
  • Delegation records. Each supervisor writes one file per UTC day, and a file nothing has written to for AppConfig:AI:Orchestration:Subagent:DelegationRetention:RetainFor (default 90 days) is deleted, so a record goes within the period plus a day. The sweep deletes only files it named, one folder below the storage path, and never follows a link, so a storage path set to a parent of the audit trails cannot reach them.
  • The chat response cache. Every cached model response expires after AppConfig:Cache:ChatResponseExpiry (default one hour, at most 30 days), in process memory and in Redis alike. Entries a Redis cache already holds from before this change have no expiry; flush the cache once after upgrading.
  • What the agent knows about a person. In the knowledge graph, what the agent remembered for someone (facts, preferences, skill-training experience), their work episodes and their episodic conversation segments are deleted once not written for AppConfig:AI:Rag:GraphRag:PersonalKnowledgeRetention (default two years). Every write stamps its time, so re-remembering a fact renews it; reads do not, because the graph does not record them. Knowledge extracted from documents, learnings and system records such as drift events are not affected. A period under a day is refused at startup and by the sweep. Cross-session memories go once not recalled or written for AppConfig:AI:Rag:CrossSessionMemory:Retention:RetainFor (default two years), from the cache and the graph database. A learning that decayed or that someone asked the agent to forget is hidden at once and removed for good after AppConfig:AI:Learnings:DeletedRetentionDays (default 30); a learning marked Permanent is kept by design. RetentionEnforcementService reads its interval live and removes at most 1,000 nodes a run, so the first run after an upgrade, which may find years of old personal knowledge, spreads the work over several runs.
  • Execution traces. A trace run (production or evaluation) that nothing has written to for AppConfig:MetaHarness:TraceRetention:RetainFor (default 30 days) is deleted. Traces hold prompts, model responses and tool payloads that cannot be found per person, so age is the only control on them and the period is kept short. A run's age is its newest file, so a run still being written is never touched and one a crash left unfinished still goes. A folder counts as a run only where the trace writer puts one, named by its run id and holding a manifest that names the same id, so a trace root pointed at a shared folder cannot reach other files. Only the files the writer creates are deleted, the manifest last so a delete interrupted by a locked file is finished by the next sweep, and links are never followed: an optimization's candidate definitions, or anything else placed in the folder, survive. The sweep runs inside a long-lived host (the first one six hours after start), so traces written by a short-lived process such as the evaluation runner are removed only by a host sharing its trace root.
  • The observability database. When enabled, a session with no activity for AppConfig:Observability:Retention:RetainFor (default 90 days) is deleted with its messages, tool executions, safety events and audit rows. Activity is the newest write to the session (starting, resuming, a turn's totals, ending) or row recorded under it, not its first start, which a resumed conversation keeps. Context snapshots and audit rows with no session go by their own age, so a conversation active for longer than the period loses its oldest snapshots. Conversation expiry and erasure remove a conversation's rows sooner; this catches what they cannot reach, such as sessions of conversations that were never stored. A conversation coming back after its session was removed starts a new one rather than writing to a row that is gone.
  • Log files. A run under AppConfig:Logging:LogsBasePath that nothing has written to for AppConfig:Logging:Retention:RetainFor (default 30 days) is deleted, except the run either file provider is writing. A run counts only when the marker the providers write at its root names it, because the logs folder is also one the file-system tool can write into; runs from before the marker existed are never swept, and a run another process is writing into the same folder is protected only by its age. Run ids and phases must each be one folder name; a sibling-folder name such as ../logsX used to pass the old check. Nothing in the shipped hosts starts a log run today.
  • Saved workflow state. A workflow nothing has saved for AppConfig:Infrastructure:StateManagement:Retention:RetainFor (default 90 days) loses its JSON checkpoint and its markdown rendering; anything else in its folder is kept. Status is not consulted, so a workflow paused at a human gate for longer than the period goes too; a deployment whose workflows pause that long sets a longer period. A folder counts only when its state file names that folder as its workflow, so a base path shared with other content cannot reach it, and a save that lands while the sweep is deleting keeps the workflow. Both files are now listed on the erasure receipt; before, neither was, because the store that writes them is built inside another.
  • Change-gate evidence. A blob nothing has stored for AppConfig:AI:Changes:EvidenceRetention:RetainFor (default 90 days, the period terminal proposals are kept) is deleted, unless an open proposal's gate decisions point at it, including a proposal quarantined because its seal failed, which is kept for investigation; storing the same content again renews it. If any open proposal cannot be read, the sweep deletes nothing. Only files named the way the store names a blob are matched, so the audit files kept beside the evidence are never reached.
  • An expired node no longer takes its source document with it. Retention removes expired graph nodes through IErasureOrchestrator.ExpireNodesAsync, which leaves the document content behind their chunk references. Before #901 it used erasure, which deleted the whole source document from both indexes when one node extracted from it aged, while it was still the source of every other node. Owner erasure still removes it.
  • Removing a document. IErasureOrchestrator.RemoveDocumentAsync takes one source document out of the corpus: its chunks from every vector and full-text collection (every page of the Azure AI Search index, which before stopped at the first thousand chunks), and what was extracted from it in the knowledge graph and the GraphRAG corpus graph. A node only that document produced is deleted; a node another document also produced keeps that document's references and survives; edges drawn from its text go; and in the corpus graph every community a changed node belongs to is deleted, because its summary was written from that text. An edge records only one source, so a relationship another document also asserts goes too, until that document is loaded again. A document id is derived from where the document came from, so this reaches every tenant and collection it was loaded into; it runs system-scoped, a store that cannot delete the chunks makes the result Partial, and every removal is audited. Operators run it through POST /api/compliance/document-removals with the document id in the body. It requires its own role, Harness.Compliance.RemoveDocument (the erasure role does not grant it, nor it erasure), and a sign-in from a tenant in AppConfig:AI:Erasure:OperatorTenantIds, the same trusted operators as erasure. It is refused while sign-in is bypassed, every request that reaches it is audited with the document id (refusals included), and it is rate limited to 30 requests an hour per operator. It is never an agent tool.
  • An optional age limit for loaded documents, off by default. A loaded document is the organisation's own business content, so by default it is kept until someone removes it. An organisation whose policy limits how long such content may be held sets AppConfig:AI:Rag:Documents:Retention:Enabled; each document not loaded for RetainFor (default three years) is then removed by the same audited removal an operator runs, recorded with retention as the actor. Loading a document again restarts its clock. The time of each load is kept in its own small database (AppConfig:AI:Rag:Documents:LoadLedgerDatabasePath, default data/documents.db), holding a document id and a time only, written before the document reaches any store; a load that cannot be recorded fails the ingest and leaves any copy an earlier load indexed untouched. (Before, any failure ahead of the store writes, such as an embedding error, also deleted that earlier copy; clean-up now runs only once this load's own writes have started.) A removal forgets the record only up to the load it judged, so a document loaded again meanwhile keeps its new time. A removal that ends Partial keeps the record and is tried again on the next sweep; at most 200 documents go per sweep, oldest first.
  • The load record is one process's file, so the age limit refuses shared stores. A removal deletes from every tenant and collection of the document stores, but the record lives under one host's folder. Where another process can write the same stores (Azure AI Search, a Postgres or Neo4j graph, another host beside this one), that host's recent load would be missing here and the document deleted for everyone. The host therefore refuses to start with the limit on unless every store is in-process (the FAISS index with the in-memory graph), a shared IDocumentLoadLedger is registered, or the deployment sets AppConfig:AI:Rag:Documents:LoadLedgerSharedByEveryWriter because every writer uses the same file on one machine; the sweep re-checks this every run. This is the same single-instance rule the architecture guide states for the other SQLite stores. Limits that remain: documents loaded before this release, or whose record was lost with a cleared base folder, have no load time and are never reached (remove them by id, or load them again); a document whose id a custom chunker formed in another shape cannot be removed by id at all, so it is not recorded and a warning is logged; and a load that lands after a removal has started but before its chunks are deleted loses that copy while keeping its record, so it should be loaded again.
  • Kept by design, with the reason in the inventory: schedules (the owner's standing instruction, identifiers only, kept until they delete it or are erased) and the call-once ledger's workflow-run rows (a run id and tool name, nothing that names a person; deleting one would re-arm a call-once tool). A conversation's ledger rows go with the conversation.
  • Loaded documents, and the knowledge drawn from them, are kept by design. They are the organisation's own business content, so the Azure AI Search indexes, the GraphRAG corpus graph and the document-derived nodes of the Postgres and Neo4j knowledge graphs keep them until the organisation removes the document, or until the optional age limit above does. Each store's entry in the inventory says so, and says what does age out beside it (personal knowledge, two years). A person's erasure still removes everything they loaded, by owner; documents other people loaded may mention them, and the erasure receipt now tells them so (below).
  • Spilled tool results (7 days), resolved escalations and terminal change proposals (90 days), orphaned token budgets (30 days) and the knowledge-graph entity types listed above already had periods.

Every store in the inventory now has a retention period or a written reason to be kept. The guard that enforced this one store at a time keeps an empty list of exceptions (src/Content/Tests/Presentation.Common.Tests/Architecture/KeptForeverGaps.cs), so a new store that keeps data with neither fails the build.

The audit archive: why erasure does not reach it, and how long to keep it

The audit trails (governance, escalation, change, egress and drift) are hash-chained, and the audit archiver moves their finished days into write-once storage (Presentation.AuditArchiver, #416). Removing one person's records from them would break the evidence they exist to provide, so erasure lists them on the receipt rather than editing them. The basis is GDPR Article 17(3): the right to erasure does not apply where processing is necessary for compliance with a legal obligation (point (b)), or for the establishment, exercise or defence of legal claims (point (e)). That basis does not remove storage limitation (Article 5(1)(e)): the archive needs an end date too, set by the deploying organisation.

  • Where the period lives. In the storage, not in the application: the archive's Azure Blob container carries a locked time-based retention policy, and a lifecycle management rule deletes day-files once that period has passed. The application never deletes from the archive; it mounts it read-only.
  • Recommended periods. Pick the longest obligation that applies and set both the lock and the deletion rule to it. As reference points: the EU AI Act requires providers and deployers of high-risk AI systems to keep the logs those systems generate for at least six months (Articles 19 and 26(6)); PCI DSS 4.0 requires twelve months of audit log history, the last three immediately available (requirement 10.5.1); sector rules (financial services, health) can require years. Where nothing longer applies, twelve months covers both of the first two. Agree the period with your data protection officer; the template cannot know it.
  • What the deletion rule must leave. Delete only the day-files ({log}/{yyyy-MM-dd}.jsonl). Keep the archive's marker file (.audit-archive), each log's witnesses/ and accepted/ folders: they hold sequence numbers, hashes and operator decisions, not the records, and verification depends on them. Verification starts at the oldest day-file that remains and logs that earlier records expired, so deleting old days does not break it (pinned by AuditArchiverTests.Verify_AfterTheOldestArchivedDayExpires_StillPasses_WithItsWitnessesAndMarkerKept).
  • Live day-files. The archiver deletes each live copy once its archived copy is safely written, so the live folder holds only days not yet archived. Without the archiver, live audit files are never deleted; running it is how they get a retention period.
  • Reducing what the trails hold in the first place is tracked in #903.

The erasure receipt reads each unsearchable store's live period: a store whose retention is running is listed as RetainedUntilExpiry with "each record is deleted within N", and one switched off is listed as kept indefinitely, which makes the receipt Partial.

i
Time is injected, not read from the wall clock

Creation and expiry are computed from TimeProvider.GetUtcNow(), an injected clock, rather than DateTime.UtcNow. That keeps retention behaviour deterministic and testable — you can fast-forward a fake clock in a test to prove expired nodes really do drop out of reads.

Right-to-erasure (GDPR Article 17)

"Delete the user's data" is easy to say and hard to do correctly, because an agent's knowledge of a user is scattered across several stores, and some of them cannot be searched for one person at all. The harness erases everything it can find for the person, lists everything it cannot, and says plainly whether the person is fully gone.

PersonalDataErasureCoordinator (src/Content/Application/Application.AI.Common/Services/Compliance/) runs the request. It reads the person's conversation ids first, and the ids their planned tasks ran under, which the plan store records against the person each time a plan starts (#906). It then erases the knowledge graph (nodes, edges, feedback weights, the vector and full-text content of linked documents, and cross-session memory) through DefaultErasureOrchestrator, then every store registered as an IPersonalDataEraser: the document indexes by owner, schedules, and, through the conversations and the planned tasks' model steps and runs, tool-result spill files, prompt-usage records, token budgets, the call-once ledger and the observability database. The conversations and the plans go next, and the token budgets and call-once ledger last, for whichever of the two was actually erased. A store reached only through a conversation or a plan is erased before it, so a failure part-way leaves something a retry can still find. A planned task run while the request runs is kept, and the receipt says to run erasure again. It runs system-scoped, so the tenant-isolated graph does not hide the person's data from an operator acting on their behalf.

Most of the stores reached through a conversation id record no owner, so erasing a conversation erases whatever they hold under its id. Every id a planned task derives contains : ({run}:{step}, planrun:{run}), and the conversation stores refuse to create a conversation whose id does (#907); the AgentHub hub and the bundle API answer with the reason. Without that, a person could name a conversation after someone else's planned-task step and have its records erased with their own. A conversation created with such an id before the rule still opens and is still erased, but erasure does not follow its id into the stores without an owner, and the receipt says so. The rule closes shapes, not knowledge: a person who learns another's randomly generated job id could still name a conversation after it.

The conversation ids are read through each store's id-only erasure listing (IConversationIdSource, #907). It loads no transcripts, and it never skips a record it cannot read: a stored conversation that cannot be read is left untouched, along with what it leads to, and the receipt gets a failed "could not be read" line. The same applies to a file whose contents name a different conversation than its file name. Failures on the erasure path are logged through MessageWithheldException, which keeps each exception's type, stack and inner chain but not its message. A store's message can name the person being erased, through a file path or an echoed owner filter, and the pattern-based log redaction does not catch ids.

A request that fails after the conversations or plans are deleted can still be retried (#907). Before deleting any of them, the coordinator records the ids it read in the erasure journal (IErasureJournal, a small SQLite database). Every later request for the same person merges those ids in, and a request clears only its own entries, once every store has erased or cannot erase at all. If the journal cannot be written, no conversation or plan is deleted and the receipt says so. Withheld conversation ids stay in the journal until its retention runs out (AppConfig:AI:Erasure:JournalRetention, a year by default, never under 90 days), so later receipts keep saying their records were kept. The same retention removes anything left by a request that was never retried. The journal holds people's ids, so it is in the personal data inventory, and clearing it also clears its write-ahead log.

Ingested documents record their owner exactly as the identity provider issued it, and their erasers match that form. A scheduled run writes under its schedule's owner, so a schedule keeps the owner as issued as well as lower-cased, and each fired run carries the issued form (#907). A schedule created before that runs under the lower-cased form until its owner next lists, reads, pauses or resumes their schedules, which fills the issued form in. Documents such a run ingested for a person whose id is not already lower-case are out of reach of erasure. Microsoft Entra object ids are always lower-case, so this only affects other identity providers.

Two ways in, both producing the same receipt:

  • Self-service: POST /api/compliance/erase-my-data erases the signed-in caller, and only them. There is no field through which another person can be named.
  • Operator: POST /api/compliance/erasures with the person's id in the body, for someone who cannot sign in. It requires the Harness.Compliance.EraseSubject role and a sign-in from a tenant listed in AppConfig:AI:Erasure:OperatorTenantIds; with that list empty (the default), operator erasure is off. The role alone is not enough, because each organisation's administrator assigns roles in their own tenant and erasure reaches every tenant. Every refusal is audited, and the endpoint is rate limited.

Both are refused while sign-in is bypassed, because every caller is then the same synthetic person. Self-service erasure is also refused for an application's own token (#907): every caller of that application shares its identity, so "erase my data" would erase all of theirs (ClaimsPrincipalExtensions.IsApplicationOnly).

  • Any issuer: a token is an application's when it carries idtyp=app, when its subject is the calling client's own id (RFC 9068's client-credentials shape; Okta names the client in cid), or when it carries Auth0's gty=client-credentials. Other providers' service accounts, such as Keycloak's, are not recognised; a host using one should turn on an explicit marker.
  • Entra workforce and External ID tokens only: a token is also an application's when it has no scp, which Entra emits only for people, or when its oid equals its sub, which is Microsoft's documented check.
  • Not applied elsewhere: other providers often give a person no scp, and Azure AD B2C makes oid equal sub for every person, so refusing on those would deny people their own erasure.

The refusal is recorded in the erasure audit trail. Operator erasure still accepts an application holding the erasure role, since an automated pipeline for data-subject requests is a legitimate caller there.

✓
The receipt says what happened in every store

An ErasureReceipt (src/Content/Domain/Domain.AI/KnowledgeGraph/Models/ErasureReceipt.cs) is a structured record returned to the caller. It carries:

  • RequestId and ScopeId, and the RequestedAt / CompletedAt window.
  • The knowledge graph's counts: nodes, edges, feedback weights, vector embeddings, full-text rows and cross-session memories actually removed.
  • Stores: one line per store, with a status and, unless it was erased, a fixed reason. Erased (with the count removed), Failed, Skipped (held back because an earlier store failed), NotSupported (a configured store that cannot erase), and three for stores that cannot be searched for one person: RetainedIndefinitely (nothing reliably ages it out, such as log files, traces, the response cache, and stores whose retention period can be switched off), RetainedUntilExpiry (its records go away on their own, such as a store held only in memory) and RetainedByObligation (the tamper-evident audit trails, kept on purpose; the line names the kinds of data each holds, for example tool inputs or the network addresses a tool reached). One more line is always there: RetainedAsBusinessContent, "documents other people loaded", telling the person that documents others loaded, and what was drawn from them, may mention them and are kept as the organisation's business content until it removes them; with the document age limit running, it adds how long.
  • Completeness and CompletenessReason. Full means every store that can find the person erased them and no store the host runs can still hold their data with no end date, other than the audit trails and the organisation's business content, which are listed with what they hold rather than counted. Any failed, held-back or unsupported store, or any store retained indefinitely, makes it Partial and names it. An earlier version of this page said that the stores on the retention gap list made every default receipt Partial; they could not, because each of them erases by owner and so appeared as an erasure line. They are now kept by design, with the reason above. Reducing what the audit trails record is tracked in #903.

The erasure audit record

Each request writes an Attempted record before anything is deleted and an outcome after, paired by a correlation id, through the shared audit sink. The record proves the erasure happened without keeping the identity it erased: it holds who asked (an operator by id; a person erasing themselves only as data-subject), per-store counts, the receipt's request id, and a pseudonymous subject reference. The reference is an HMAC-SHA256 of the person's id under AppConfig:AI:Erasure:SubjectReferenceKey (base64, at least 32 bytes): whoever holds the key can recompute it from an id and find that person's erasure, and no one without the key can reverse it. Without a key, no reference is recorded. A missing key or a broken audit sink never blocks an erasure. Log lines on the erasure path carry neither the person's id nor their conversation or memory ids.

Deleted text on disk

SQLite normally marks a deleted row's space free without clearing it, so erased text could still be read from the database file. Every SQLite connection the harness opens turns PRAGMA secure_delete on, through SqliteSecureDelete and UseSqliteWithSecureDelete, and the full-text index also sets FTS5's own secure-delete option so deleted words leave its index immediately. The databases run in write-ahead-log mode, where a deletion first lands in a side log and the old page stays in the main file until a checkpoint, so once every store has deleted, each SQLite store empties its log (wal_checkpoint(TRUNCATE), through IPersonalDataScrubber). This is a separate pass, on every request: when another connection is mid-read and a log cannot be emptied, the receipt gets its own Failed "(deleted bytes)" line without marking the delete itself failed or holding back the stores after it, and a retry empties the log even though there is nothing left to delete. A test erases a person and scans the database files and their logs for their text while the host's connections are still open. Limits:

  • It covers deletes from now on. Rows deleted before this change can remain in free pages until a one-time VACUUM of each database; for the full-text index, run its optimize (or rebuild) command first, because words of rows deleted before secure-delete was on sit in live index segments, which VACUUM keeps.
  • Copies outside the database file are out of its reach: backups and snapshots taken before the erasure, and blocks the file system has not reused. Retention of backups is an operational control.
  • With FTS5 secure-delete in use, the full-text database can no longer be read by SQLite older than 3.42; the bundled SQLite is newer.
  • External stores (Azure AI Search, PostgreSQL, Neo4j) manage their own storage and deletion guarantees.

Data-classification DLP

Isolation and retention govern where data lives; data-loss prevention governs whether a tool call may move it at all based on its sensitivity. The harness ships a Microsoft Purview classification gate, IToolClassificationGate, that runs on the live tool-execution path — one of the three ambient gates inside GovernedAIFunction (see Tools & Permissions). It classifies the data a tool touches against Purview sensitivity labels and acts on the verdict.

It is opt-in through a single mode knob, AppConfig:AI:Governance:DataClassification:Mode:

  • Off (default) — the gate is inert; no classification runs.
  • Audit — classifications are computed and logged, but nothing is blocked or altered.
  • Enforce — verdicts act. A Block verdict returns a model-facing message instead of running the tool; a RedactOutput verdict lets the tool run, then scrubs the result through ICompositeResponseSanitizer and additionally through IContentRedactionFilter's known-secret-pattern scrub — strictly more than the unconditional sanitize every other tool result already gets — before it re-enters the model's context.

The gate fails open on ambiguity by design: an Unknown classification maps to Allow, and the whole subsystem stays dormant unless both a mode other than Off and a classification provider are configured. This keeps the closed-by-default posture on capabilities while avoiding false positives that would block legitimate work in deployments that have not adopted Purview labelling.

Secrets management

The data the agent holds is one thing; the credentials that let it reach databases, model endpoints, and APIs are another. None of them belong in source. Configuration is assembled by LoadAppConfig in src/Content/Presentation/Presentation.Common/Helpers/AppConfigHelper.cs, which layers sources in ascending priority — later layers override earlier ones: 

appsettings.json
  -> appsettings.{Environment}.json
  -> User Secrets (development only)
  -> environment variables
  -> Azure Key Vault (non-DEBUG builds only)
  -> Azure App Configuration

Key Vault is wired in for non-DEBUG builds via: 

builder.Configuration.AddAzureKeyVault(
    new Uri(akvUri),
    new DefaultAzureCredential());

The credential is DefaultAzureCredential — authentication is Entra managed identity, with no stored credential anywhere in the app to leak. No secret is hardcoded, and a missing required secret fails host startup loudly rather than letting the app run in a half-configured state. The Key Vault settings are bound through src/Content/Domain/Domain.Common/Config/Azure/KeyVaultConfig.cs.

Attack scenario: reaching across the tenant wall

✕
A user tries to recall another tenant's data

Suppose a user in tenant A crafts a request designed to pull back a fact they know exists in tenant B — perhaps they learned a competitor's record id, or they try to address a memory key by guessing its name. Their request is authenticated as a tenant-A user, and that identity is set in the AsyncLocal accessor at the middleware before any retrieval runs.

When retrieval reaches the graph, every candidate record passes through TenantIsolatedGraphStore's per-record check. Tenant B's nodes have TenantId = B, which does not match the caller's tenant — the tenant check fails and those nodes are filtered out before they ever reach the model's context. The query returns nothing across the wall. Even the namespaced memory id (memory:B:…) can't be reached, because the caller's scope is A and the id space is partitioned by scope. No leak, no error message that confirms the record exists — just an empty, scoped result.

That closes the seventh and final layer. With identity, autonomy, tool permissions, execution, egress, content safety, and now data protection all in place, the last question is how you prove they stay in place release after release. That is the job of the OWASP Agentic evaluation pack — ten deterministic tests, one per threat category, that attack each layer and fail the build if a defence has quietly regressed.
