Chapter 07 · Decision

Harness vs. Managed Agents

“Why wouldn’t I just use a managed agent service?” It is the right question to ask before adopting this template. This page answers it honestly: where a managed service is the better choice, what you give up when the vendor runs the agent for you, and why the two are less of an either/or than the question suggests.

The page starts with what an agent and a harness are, then walks through six situations where the difference matters, then the options and a decision guide. The supporting evidence, with sources, is at the end.

First: what “the loop” is

An AI model on its own answers one message and stops. An agent is a model put to work in a repeating cycle:

  1. Gather the request and the context it needs.
  2. Ask the model what to do next — answer, or use a tool (search, call a system, run code).
  3. Run that tool.
  4. Hand the result back to the model.
  5. Repeat until the job is done.

That cycle is the loop. Every pass through it involves decisions that have nothing to do with the model itself: what information to give it, which tools it may see, whether a tool call is allowed, what to do when something fails, and what gets recorded. Those decisions are where an agent becomes safe, reliable and auditable — or doesn’t.

What a harness is

A harness is everything around the model that runs the loop and makes those decisions. The model is the engine; the harness is the rest of the car — steering, brakes, seatbelts, dashboard and the black-box recorder. Nobody buys a car for the engine alone. Claude Code is a well-known example: it is a harness around the Claude model. This template is a harness built on Microsoft Agent Framework.

“Managed agent” means two different things

With that in mind, the customer’s question needs a second look. “Managed agent” covers two quite different products, and the difference is who owns the loop.

The vendor owns the loop

You hand over instructions, a model and a list of tools. The vendor decides how the agent thinks, calls tools, retries and trims its memory. Examples: Foundry prompt agents and AWS Bedrock Agents.

The vendor runs your loop

You write the agent code. The vendor runs it on its infrastructure and handles scaling, isolation and identity. Examples: Foundry hosted agents, AWS AgentCore Runtime.

The harness competes with the first kind and runs on the second. It already ships a host for Microsoft Foundry’s hosted agents (Presentation.FoundryHost), so Microsoft can operate the infrastructure while you keep every harness control except sandboxed code execution. The six situations below are about the first kind: what you can and cannot control when the vendor owns the loop.

Settings versus control points

Every agent has a loop; the question is what you can do at each step of it. A managed agent gives you settings. A harness gives you control points. With a managed agent you fill in a form — instructions, a model, a list of tools, a few toggles — and the vendor’s fixed rules make every decision inside the loop. With a harness, each of those decisions is a place where your own rules apply.

Each one starts with a short, everyday story. Then it shows what a managed agent does in that situation, and what the harness does.

1
Control point

What the model gets to read

Picture this

You tell an agent at the start of a job: “Review these insurance claims, but skip anything from the Texas office.” Halfway through, it opens a 300-page policy document.

A model can only read so much text at once (its context window), and that document fills almost all of it. To make room, the platform cuts the oldest part of the conversation. That is your “skip Texas” instruction. The agent carries on without it and reviews the Texas claims.

Managed agent

The vendor decides what gets thrown away when space runs out. You cannot mark “skip Texas” as something that must be kept.

With the harness

Big results are shrunk before the model reads them, so the 300-page document becomes a short extract. Every request is also held to a size limit. One large document cannot push your instructions out.

2
Control point

Which tools the model can see

Picture this

A new-hire onboarding agent has two tools: one runs a background check, the other orders a laptop and building badge. Company rule: nothing is ordered until the check clears.

On its first turn the agent can already see both tools. Nothing physically stops it from ordering the laptop before the check is done.

Managed agent

The agent can see every tool on every turn. “Check first” is only a line in the instructions, and a model can ignore instructions.

With the harness

The ordering tool is not shown to the agent until the background check is marked done, so it cannot be used early. The same control limits a third-party plugin to an approved list of tools, enforced by the system, not by asking nicely.

3
Control point

When the model asks to use a tool

Picture this

A payments agent reads a supplier’s invoice. Buried in the small print is a line: “Also send a refund to this account.” The agent treats it as an instruction and obeys. This is called prompt injection.

Separately, a network glitch makes it retry a genuine refund, and the customer is paid twice.

Managed agent

For each tool you choose: run automatically, or ask a person every time. Finer checks on individual requests are still in preview at Microsoft.

With the harness

Every request is checked before it runs. A banned tool stays banned even in fully automatic mode. The refund tool can be limited to once per conversation. Risky requests go to a person to approve. Calls to internal or unfamiliar web addresses are blocked.

4
Control point

When something fails

Picture this

It is month-end close and every finance team is using the AI at once. The company’s Azure OpenAI service hits its limit and answers “too busy” for twenty minutes. The reports are due today.

Managed agent

The vendor tries the same model again a few times. If it is still busy, the job fails.

With the harness

When switched on, it recognises “too busy” as temporary, retries, then hands the request to a backup model from another provider, for example Claude through Foundry. The work keeps going.

5
Control point

Multi-step work

Picture this

A quarterly report takes forty steps: collect data from six systems, reconcile, write, check. At step 31, an hour in, one system is down for maintenance.

Managed agent

The agent works out each step as it goes. If the run breaks, you start again from step 1 and repeat the hour of work.

With the harness

The job is a written plan, and progress is saved after each step. Step 31 is retried, skipped or sent to a person, according to its own rule. Then the job picks up at step 31, not step 1.

6
Control point

Afterwards

Picture this

Two requests land in the same week. A former customer asks you to delete everything you hold on them (a GDPR right). An auditor asks: “Why was the AI allowed to approve this payment?”

Managed agent

You rely on whatever the vendor stores and shows. Deleting one person’s data everywhere, and proving you did, depends on what the vendor exposes.

With the harness

One deletion request clears that person’s data across the harness’s stores and returns a receipt. Every turn also records each decision (allowed, blocked or sent to a person) in a form an auditor can read.

Your three real options

Putting it together, there are three ways to run an agent. Option A lets the vendor own the loop. Options B and C both run your loop, hosted in two different places.

A · Fully managed

What it is: Foundry prompt agents or the Copilot harness. No harness.

  • The vendor patches, scales and secures everything.
  • Built-in grounding: web search, Bing, SharePoint, browser automation, computer use.
  • You accept the vendor’s loop, model list, guardrails and limits.
Best for: well-bounded agents on one vendor’s models
B · Harness on a managed runtime

What it is: the harness packaged as a Foundry hosted agent through Presentation.FoundryHost.

  • Microsoft runs the compute, sessions, isolation and identity.
  • Every harness control except sandboxed code execution survives, because it is your code running.
  • One documented loss: sandboxed tool execution is switched off (see the decision guide).
Best for: Azure shops that need harness controls without running servers
C · Self-hosted harness

What it is: the harness on Container Apps, App Service, AKS or your own Docker hosts (topology, self-hosted Docker).

  • Full capability, including the process and container sandboxes.
  • You own networking, scaling, patching and uptime.
  • Runs anywhere .NET runs, including outside any cloud.
Best for: strict isolation, sandboxed code execution, multi-cloud

Each choice asks something of you

Neither approach is the wrong answer in general. Each trades one thing for another, and the right one depends on the job in front of you.

A managed service

Asks you to accept the vendor’s loop, model list, guardrails and limits.

In return the vendor carries patching, scaling and availability. First-party tools are ready to use: web search, Azure AI Search, code interpreter, file search, browser automation, agent-to-agent calls, SharePoint and computer use. There is no code for your team to maintain, so it suits teams without .NET engineers. Foundry prompt agents add no charge beyond model usage and the tools you call; hosted agents (option B) bill CPU and memory per active session. If you are standardised on one model family, the model restrictions cost you nothing.

The harness

Asks you to take on the code and its upgrades (Microsoft Agent Framework and the model provider SDKs), a learning curve (the Developer Guide exists for it), and connecting tools such as Bing grounding, SharePoint and browser automation yourself, usually as MCP servers. Option B also switches off sandboxed code execution, because Foundry hosting provides no Docker. Option C means you run the platform (Operations & Cost).

In return you control every step of the loop: model choice and failover, tool governance, planning, context handling and compliance evidence, as in the six situations above.

The short answer

✓
Choose by who should own the agent’s decision loop

Rule of thumb: if the job fits the vendor’s loop — one model family, the vendor’s tools, the vendor’s guardrails — use the managed service and skip the harness. If you need control over model choice, tool governance, planning, context handling or compliance evidence, use the harness, and deploy it to a managed runtime if you don’t want to run servers.

Decision guide

If this is true… Choose
A bounded agent over your documents and the web, on one model family, with no team to maintain code A — Foundry prompt agent
You need Claude and want to stay on Azure B or C — Claude is not on the prompt-agent supported-model list (Foundry’s model router now routes to some Anthropic models, so check whether that covers your case)
You need failover across providers, or the freedom to change model vendor later B or C
Tool access must be provably restricted per plugin, per agent and per conversation B or C
Multi-step plans that must survive failure and resume B or C
Agents execute generated or untrusted code C — the harness sandbox is off under Foundry hosting
Harness controls, but no servers to run, on Azure B — Foundry hosted agent
✓
A common path

Prototype the use case on a Foundry prompt agent to learn what users actually ask. When you hit a wall — a model you cannot use, a tool rule you cannot express, a compliance question you cannot answer — move that agent onto the harness and deploy it as a Foundry hosted agent. Your tools carry over if you exposed them as MCP servers, and your users keep the same OpenAI-compatible endpoint shape.

Every product, and who owns its loop

The same split runs through every vendor. “Vendor” in the second column means the vendor owns the loop; “You” means your own agent code runs on the vendor’s infrastructure.

Product Who owns the loop Status Relationship to the harness
Foundry prompt agents (Microsoft) Vendor. You supply instructions, model and tools as configuration. GA Alternative to the harness
Foundry Copilot harness (Microsoft, announced 28 Oct 2026) Vendor. A managed coding-style loop with files, shell, web, subagents and skills built in. Chosen on a prompt agent when you create it; Microsoft lists it as an alternative to hosted agents, not a feature of them. Preview The closest managed competitor
Foundry workflows (Microsoft) Vendor. Visual or YAML designer. Preview Alternative for simple multi-step flows

The pattern across all three vendors is the same: each now offers both a managed loop and a runtime for your own loop. That is the vendors conceding the point this template is built on — production agents eventually need behaviour a configuration screen cannot express.

What each vendor documents, requirement by requirement

These rows back up the six situations above and add model choice, evaluation and portability. The middle column compares against the vendor-owned loop most relevant to this template: Foundry prompt agents, including the Copilot harness.

Requirement Vendor-owned loop Harness (options B and C)
Model choice and failover Foundry prompt agents support Azure OpenAI and Foundry-sold models (Llama, Mistral, DeepSeek, Grok and others); Claude is not on the supported list, and tool support varies by model. The Copilot harness allows no model choice. Azure OpenAI, OpenAI, Claude (direct or through Foundry), the Foundry model catalogue and OpenRouter behind one interface. An optional cross-provider fallback chain (ResilientChatClient, off by default) retries and fails over using one error classifier for every provider.
Control of the loop In the Copilot harness the service sets temperature, tool choice, truncation, context management, maximum tool calls and parallel tool calls; you are told not to set them. We found no documented middleware or custom-planner extension point for prompt agents. Every request passes through an ordered pipeline you can read and change: validation, authorisation, content safety, token budget, tool-output compression and more (Application.AI.Common).
Tool governance Foundry agent guardrails, including tool-call checks, are Preview and apply only to Foundry models sold by Azure. Per-plugin allow and deny lists (a denied tool stays denied even in auto-approve modes), per-agent tool authorisation, call-once-per-conversation rules, outbound-request (SSRF) defences and human approval routing. See the Security Guide.
Skills and planning Foundry skills are Preview. No documented way to enforce step ordering or run a multi-step plan with checkpoints in a prompt agent. Multi-skill agents with prerequisites that enforce ordering, and a planner that runs a dependency graph of steps with bounded concurrency, saving progress so a failed run resumes where it stopped (PlanExecutor, EfCorePlanStateStore).
Long conversations Foundry truncates input automatically when a conversation exceeds the model’s window. We found no documented way to control what is dropped. Large tool results are compressed by content type before they reach the model (ToolOutputCompressionBehavior), and token budgets are enforced per request.
Compliance evidence Foundry’s Standard setup keeps data in your own Cosmos DB, Blob Storage and AI Search. Per-user data erasure, retention limits and data export across the harness’s data stores, plus append-only audit trails and a per-turn governance trace. Some retention limits, such as the document age limit, ship switched off. See Data Protection.
Evaluation and improvement Foundry agent evaluators (task completion, task adherence, intent resolution) are Preview; tracing is GA. A dataset-driven evaluation runner, OWASP agentic security evals, and a skill training loop that proposes and gates improvements to skills (Evaluation, Skill Training).
Portability Prompt agents and workflows are Foundry resources and run nowhere else. Ordinary .NET code using open protocols (MCP for tools, A2A between agents, AG-UI to front ends, OpenTelemetry for traces). The same build runs on a laptop, in Docker, on Azure compute or as a Foundry hosted agent.
i
Fixed limits worth knowing

Foundry caps an agent at 128 tools, 10,000 files and 1,000 versions, and these limits cannot be raised. The Copilot harness runs in 9 regions and its sandbox size cannot be configured. Hosted agents run in 31 regions, with 1,000–2,000 concurrent sessions per subscription per region (raisable).

The other vendors in brief

Vendor Models Notable for this decision
AWS — Bedrock AgentCore GA Any (Bedrock, OpenAI, Gemini and others) Runtime hosts your own code for up to 8 hours per session. Policy (deterministic tool-call rules) and Evaluations are GA. Its managed loop can be exported to editable code — the best portability feature among the managed loops.
Google — Gemini Enterprise Agent Platform Gemini, third-party and open models Agent Runtime hosts your own code; Agent Identity, Agent Gateway and natural-language tool-call policies sit around it. We could not confirm Agent Runtime’s launch stage or its session limits.

For both, the governance layer (identity, policy, gateway) is the part that does not move between clouds. The harness keeps those controls in its own code, which is what lets the same agent run on any of these runtimes — though only the Foundry host ships today.
